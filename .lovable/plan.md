### ERROR 2 — Missing RLS on service_tickets
**Status: Already covered, but the proposed SQL has a bug.**

The `service_tickets` table already has 5 RLS policies:
1. **"Attendees can view own tickets"** (SELECT) — joins through `attendee_services` → `attendees` → `auth.uid()`
2. **"Authenticated read own service tickets"** (SELECT) — same logic (duplicate)
3. **"Event staff can manage tickets"** (ALL) — coordinator/field_manager with `is_event_staff` check
4. **"Superusers can manage all tickets"** (ALL)
5. **"block_anon_access"** (SELECT, RESTRICTIVE) — blocks anon

The proposed SQL references `attendee_services.event_id` which **does not exist**. The `attendee_services` table has no `event_id` column — the path to events goes through `attendee_services` → `attendees.event_id` → `events`.

However, there is a gap: no **org-level admin** policy exists (only event staff and superusers). I will add a corrected admin policy using the proper join path.

### Migration SQL (corrected)

```sql
-- Org admins can manage service_tickets in their organization
CREATE POLICY "Admins manage org service tickets"
ON service_tickets FOR ALL TO authenticated
USING (
  EXISTS (
    SELECT 1
    FROM attendee_services aser
    JOIN attendees a ON a.id = aser.attendee_id
    JOIN events e ON e.id = a.event_id
    WHERE aser.id = service_tickets.attendee_service_id
      AND e.organization_id = get_user_organization(auth.uid())
  )
);
```

This uses the correct join path: `service_tickets` → `attendee_services` → `attendees` → `events` → `organization_id`.

### Technical Note
The `client.ts` file with hardcoded URL/anon key is auto-generated by Lovable's Supabase integration. The anon key is a **publishable** key (not a secret) — it is safe to have in client code. The real protection comes from RLS policies.
